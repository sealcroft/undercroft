Undercroft architecture

How a memory is stored, protected, and found again — the palace model, the retrieval stack, the write path, and every knob that changes their behaviour.

Engine v1.0.0 · light and dark themes, following your system by default · diagrams also available as SVG and PDF

The one idea

Most memory systems summarise what you tell them. Undercroft stores the words and adds structure alongside them.

That single decision explains almost every design choice below. If content is kept verbatim, then retrieval has to be good enough to find the right passage rather than relying on a pre-digested summary — hence a hybrid lexical + semantic stack with optional reranking. If nothing is thrown away, then metadata that arrives with the content has to be preserved too, not just the text. And if the store holds the user's actual words, it had better be encrypted, integrity-tagged, and tamper-evident.

Verbatim

The write path never summarises, paraphrases, or lossily compresses. Only derived structure is added; the text is returned exactly as given.

Local-first

Default builds have no telemetry dependencies, contact no external API, and use a deterministic offline embedder. Every outward path is an explicit opt-in.

Provable

Every row carries a keyed HMAC verified on read; every write advances a tamper-evident audit chain inside the same transaction.

Palace, wing, room, drawer →

Palace, wing, room, drawer

Four nested levels, each with exactly one job.

Drawer — the unit of memory

One verbatim chunk of content plus its metadata. Its identity is deliberately structural, not content-based:

drawer_id = hash(wing, room, source, chunk_index, normalize_version)

Content is not in that hash. This is what makes re-mining a source idempotent: process the same file twice and the same chunk lands in the same slot, updating in place instead of creating a duplicate. It also means changing any of those five inputs changes the drawer's identity — which is why giving room new meaning only applies to newly created vaults.

A save that arrives through an API has no source to be the fourth chunk of, so chunk_index carries a unique append index instead of a position, and identity becomes unique-per-call rather than idempotent: posting the same text twice creates two drawers. That is the intended reading — the same words written on a different day are a different event, not a mistake to be silently swallowed. Collapsing repeats is deduplication's job, and it keeps every date the text appeared on rather than discarding all but one.

The append index has to be monotonic. It once came from COUNT(*), which decreases when a drawer is deleted — so the next save was handed an index still in use, derived an id that already existed, and overwrote the unrelated drawer holding it. It now comes from SQLite's AUTOINCREMENT sequence, which never reuses a rowid.

Room — topic, session, or ticket

A room groups drawers within a wing and doubles as a search filter. Because it is both a label and a predicate, it can carry real structure — one room per conversation session, per support ticket, per meeting — at no extra cost. The distilled knowledge surface uses this: fact-drawers live in their own room (facts by default), so a caller chooses between verbatim recall, distilled facts, or both purely by varying the room filter.

A model may point, not assert

Distillation runs through an approximate component, so nothing it says is taken on trust. It is asked for quotations — the words that date a fact, and the words that support it — and the engine checks each span against the note it supposedly came from. A span the note does not literally contain is not evidence and contributes nothing, so a model that answers with a computed date instead of a quotation simply adds nothing. Only the deterministic layer ever turns words into a date.

That check is what makes a fact's grounding knowable: stated when the note's own words support it, background when they do not, and unevaluated for facts distilled before the check existed — three states, because "we did not look" and "we looked and found nothing" are different claims. Background is a provenance kind, not a quality grade: "Leeds is in the United Kingdom" is absent from the note and is exactly the edge that answers which country someone works in. Filtering is opt-in and the default returns all three, because excluding background facts would break the multi-hop questions a graph exists to answer.

Wing — the isolation unit within a vault

A person, a project, or a tenant's user. Search is normally wing-scoped, so a wing bounds how much work every retrieval stage has to do.

Vault — the cryptographic boundary

Each vault has its own key, derived from the palace master key via HKDF, and every sealed artifact binds the vault identity into its AEAD associated data. Cross-vault access therefore fails cryptographically, not merely because a check rejected it. One vault is one SQLite database with one audit chain.

Design note

Metadata rides inside a single serialized meta_json column that the row's HMAC already covers. Adding an optional metadata field therefore needs no schema migration and leaves existing rows byte-identical — their tags still verify. That property is why content_date, time_mentions, and entities could be introduced without touching storage or keys.

Layers and trust boundaries

One process holds one palace. Tenancy is expressed as vaults, not as separate palaces.

Callers reach the engine three ways — MCP over stdio for local agents, HTTP /v1 for applications, and the CLI — and all three land on the same store. An admin console is served at /ui on every build.

Two components sit deliberately outside the engine. The orchestrator is a separate binary and a pure /v1 client: it maps tenants to vaults and proxies requests, and the engine never links it. Remote vector backends (Qdrant, Chroma, pgvector, Milvus, Weaviate) are treated as untrusted accelerators — they receive sealed payloads only, and anything they return is re-verified locally before use.

The write path

Normalise, derive, embed, then commit everything atomically.

Normalisation has two modes

A safety floor applies always: NUL and lone control characters are stripped (they corrupt terminals and log pipelines) and CRLF becomes LF so hashes are stable across platforms. Tabs and newlines always survive.

ModeAdditional behaviourChosen for
Prose defaultTrims trailing whitespace per line, collapses 3+ blank lines to 2 — but never inside a fenced ``` or ~~~ blockMarkdown, notes, chat messages
CodeSafety floor only. Every byte of indentation, every trailing space, every blank run is preservedSelected by file extension: .py, .rs, .ts, .sh, .yaml, Makefile, ~75 more

The reason for the split is simple: in a Python file leading whitespace is the semantics, and a trailing-space diff is a real change. Tidying it away is a silent edit to user data. normalize_version is stamped into each drawer's metadata and into its id, so a change in normalisation output is detectable rather than invisible.

Derived structure — added, never substituted

FieldWhat it holdsHow it is produced
content_dateWhen the content happened, as opposed to filed_at — when it was written downSupplied by the caller. Ingesting a year-old conversation today makes those two dates a year apart
time_mentionsDates and times written inside the text, each span kept verbatim with its byte offset, plus a resolution when derivableDeterministic offline scanner. Absolute forms resolve alone; relative ones ("yesterday", "last Tuesday", "three weeks ago") resolve against content_date
entitiesNames appearing in the content, lowercased and deduplicatedDeterministic offline extractor; sentence-initial words excluded as noise
occurrencesFurther days this same content was recorded, beyond the drawer's ownWritten only by deduplication. Collapsing identical text is right — it is the same text — but the days it appeared on are data, so they move to the survivor before the duplicate row goes
Derived at write, read live

time_mentions is recorded onto the drawer when it is written, and re-read when it is served. The resolution depends on nothing but the drawer's own text and its content_date, both immutable — so storing it only freezes it at whatever the writing binary understood. A drawer written before "last month" was read as a month still carries it as a single day; re-reading upgrades it without rewriting a byte, which is what makes a scanner improvement reach existing vaults with no migration. The stored copy remains the record of what was understood at the time, and the two are reported as disagreeing rather than one silently winning.

It is also what makes language a read-time choice. The scanner is selected per request, so a corpus ingested while the engine read English is answered correctly the moment a reader asks in Arabic — no re-ingest, no rewrite. And a language is a scanner, not a word list: Arabic puts the past marker before the count (قبل ثلاثة أيام), has a dual that is one inflected word rather than a numeral beside a plural (يومين), puts period modifiers after the noun (الأسبوع الماضي), reads two current Gregorian month-name systems, and begins its week on Saturday. Each of those is grammar, and none of them survives being translated into an English pattern.

Note what this does not do. Reading dates inside the text is the scanner's job; retrieving across languages is the embedder's, and the default embedder cannot — it hashes surface forms, so an English query and an Arabic note share no token and no character trigram. The two are chosen independently, and a multilingual vault needs both.

Never guess

With no anchor, a relative time mention is recorded unresolved rather than assigned a plausible date. An honest gap is useful; an invented date is the failure mode this design exists to remove. The extraction runs inside the drawer constructor rather than at each call site, so no write path — REST, MCP, CLI, mining, import, sweeper — can silently skip it.

One transaction

Sealing the content and embedding, computing the row tag, and appending to the audit chain all happen inside a single SQLite transaction. There is no committed write that lacks its audit entry. Bulk ingest takes one transaction and one manifest anchor per batch rather than per drawer, measured at roughly 55× fewer fsyncs on a 200-drawer import.

The asymmetry is the detector

The manifest anchor is fsynced after the transaction commits, so it deliberately lags the database. At open: anchor behind the database means power was lost mid-write, and it fast-forwards. Anchor ahead of the database means someone restored an older copy of the file — a tamper alarm. Keeping them merely "in sync" would make those two cases indistinguishable; the directional invariant is what makes rollback detectable.

The retrieval stack

Seven stages. Two are optional tiers that are off until you enable them.

Stage 2 — candidate prefilter opt-in

By default there is no prefilter at all: search scans every live drawer inside the declared scope, exactly. Past a certain size that becomes the dominant cost, and three approximate tiers exist to avoid it: PQ/IVF clusters vectors into lists and probes only the nearest ones (roughly O(√N)), MUVERA FDE gives token-aware candidates, and an experimental in-memory HNSW graph gives O(log N).

Measured

On a deliberately adversarial 20,000-drawer corpus (every query lexically matching every drawer), flat scan ran at 499 ms p50 while UNDERCROFT_RETRIEVAL=pq ran at 12 ms p50 — a 41× difference. Two caveats before enabling it anywhere that matters: these tiers are approximate, so recall must be checked against a flat baseline first; and the first query after ingest pays a one-time index build, which wants warming at startup rather than ambushing a user. The 66 s that build took in that same test is no longer representative and is left here only so the shape is not mistaken for the cost: the rebuild loop wrote one row per autocommit insert, which under synchronous=FULL is one fsync per row, and roughly 95% of that number was disk syncs rather than computation. One transaction around the rewrite removed it — a smoke warm-up went 36.2 s to 2.3 s — and the build is now CPU-bound, with full-scale figures still to be measured.

Stage 3 — verify, decrypt, score

Every candidate row's HMAC is verified before its content is used; integrity is not an optional tier. Scoring then fuses a lexical BM25 signal with cosine semantic similarity — each channel calibrated to a fixed scale, never normalized against the result set. UNDERCROFT_FUSION selects bm25 (the default) or legacy; the former rrf mode measured below both and was removed (setting it warns and falls back to bm25).

Stage 4 — the relevance gate

An unrelated record still scores around 0.35 from the neutral cosine midpoint alone, so the gate demands actual evidence: lexical > 0 || semantic > gate. Failing rows are removed, not merely down-ranked.

That threshold is a property of the embedder, not a constant. The default hashed embedder puts unrelated text at a cosine of almost exactly zero, so its gate sits at 0.56 — but a trained encoder does not behave that way at all, and E5- and BGE-family models place unrelated pairs near 0.75. A single shared number would therefore sit below a model's floor, making the disjunct vacuously true for every hit and silently retiring the gate. Each embedder now declares its own gate or has it measured against known-unrelated probe pairs at open; an external vault, whose vectors come from a model this process has never seen, refuses semantic-only admission until an operator declares one. UNDERCROFT_SEMANTIC_GATE overrides it.

Known limitation

Because lexical > 0 passes on any shared term, this gate rarely empties a result set in practice. A caller cannot use "the gate rejected everything" as a signal that the corpus lacks an answer — measured on an adversarial benchmark, unanswerable questions received exactly as much context as answerable ones. Deciding that retrieved text fails to answer a question requires reading it against the question, which is the answering model's job, not retrieval's. What the layer does provide is per-hit score, semantic, and lexical values so a caller can set its own policy.

Stage 5 — second stage opt-in

A cross-encoder rescores the top-N candidates on the full (query, content) pair — the interaction a bi-encoder cannot capture — then results are re-sorted. Alternatively ColBERT late interaction computes MaxSim over token matrices built at ingest. Bounded to UNDERCROFT_RERANK_TOP_N forward passes, default 50. Late interaction has its own depth, UNDERCROFT_LATE_TOP_N (default 200): MaxSim costs arithmetic per candidate rather than a forward pass, so it can look far deeper than a cross-encoder can afford to. Measured worth +2.1pp of turn-level evidence delivery on LoCoMo with the token codebook disabled — the one configuration where two runs are comparable; in the shipped v2 packing the same step measured +1.7pp and +0.0pp, so its default-configuration value is not established.

Stage 6 — select top-k

Results are truncated to the requested limit. An optional room_cap takes at most N hits per room and then refills any remaining slots in score order — a soft cap, so a genuinely single-room question still receives the full limit and recall is never traded for spread.

Measured — enable with care

On a corpus where evidence is concentrated (one session holds the answer), room_cap=2 measured 5.6 points worse overall. Forcing room diversity pulls in unrelated sessions and displaces the chunks that actually contained the answer. Spreading trades precision for breadth; when precision is what the question needs, that trade loses. Default off for this reason.

Stage 7 — assemble context caller side

The final step belongs to whoever builds the prompt: label each hit with its content_date, optionally order them chronologically, then hand the text to the model.

Recall vs precision, measured

Different stages control different failure modes — worth knowing before tuning any of them.

PropertyDecided atWhat goes wrong when it is weak
Recall — is the evidence findable?stages 2–5The answer is not in the candidate set at any k. Fix: better ranking or a wider pool
Precision — is the evidence shown?stage 6The answer ranks below the budget. Fix: raise k, or select differently
Interpretability — can it be read?stage 7Evidence is present but unusable — "I went yesterday" with no anchor
Worked example

Questions needing evidence from several sessions were failing. Measuring gold-document presence separated the causes cleanly: where all the required documents reached the context, answers were correct 97% of the time; where one was missing, they failed. Probing recall at increasing k showed the missing documents ranked between position 10 and 50 — findable, but below the budget. That made it a stage-6 problem, ruled out reranking (stage 5) as the fix, and explained why forcing room diversity had made things worse: the issue was depth of recall for weakly-matching evidence, never spread.

The same measurement also showed roughly 40% of those failures had every required document present and still answered wrongly — an aggregation limit of the answering model that no retrieval change can lift. Knowing which portion is which prevents spending effort on the part that is not retrieval's to solve.

Languages

Nineteen languages reach 100% of an audited paradigm on the lexical channel — and none of them has to be declared.

Three separate things can stop a query from finding a drawer that visibly contains its answer, and they fail in different layers. The word may be spelled differently — a diacritic, a ligature, a different Unicode normalisation form. The script may not mark word boundaries at all, so there is nothing to split on. Or the drawer may hold the word in a different grammatical form — a plural, a case ending, an Arabic broken plural sharing barely any letters with its singular. Dates add a fourth problem of their own: the words a writer typed beside a number decide which calendar counted it.

These are handled in different places by deliberately different mechanisms, and it is worth knowing which is which, because none of them substitutes for another. Folding cannot reach morphology; segmentation cannot fix a diacritic; and no amount of either delivers cross-lingual retrieval, which belongs to the embedder alone.

The fold, and what it deliberately leaves alone

Every comparison — query against drawer, on both the lexical and the embedding side — runs over a folded comparison key, never over the stored bytes. The stored bytes are the user's words and stay exactly as given; the fold exists only so that two spellings of one word can meet.

Stage order carries a real constraint. Lowercasing must happen before marks are stripped, because İ is not a combining mark and the strip cannot see it — lowercasing is the operation that manufactures the U+0307 that the strip then removes. That single ordering is why İZMİR folds to izmir rather than tokenising to the fragment zmi, with no Turkish-specific special-casing anywhere in the code.

Pinned as NOT stripped

A fold that removes everything invisible is wrong, and each exception is held by a test. ZWSP is Khmer's word delimiter — stripping it destroys the only boundary that script has. ZWJ is contrastive in Malayalam, so removing it changes the word. And a blanket decompose-and-strip over Cyrillic turns й into и, merging two distinct letters; Cyrillic therefore gets only a narrow stress-mark rule plus ё→е.

Splitting a script that has no spaces

Splitting on "not alphanumeric" finds no boundary whatsoever in Han, Kana, Hangul, Arabic, Khmer, Thai, Lao or Myanmar — every one of those characters is a Unicode letter, so an entire clause used to become a single token. The consequence was not bad ranking. Search drops a hit that has no lexical evidence and only a neutral cosine, so a query for a word the drawer plainly contained returned an empty result set.

Segmentation emits bigrams over maximal same-script runs, and unigrams only where a single character is itself a unit of meaning — which is Han, and Han alone. Emitting unigrams in an alphabetic script would make قطار "match" المستشفى on a shared alef, and since a hit is admitted on any lexical evidence at all, that does not merely add noise to the ranking: it retires the relevance gate.

Measured — why an n-gram is refused the exact channel

A bigram is a fragment, not a word, so tokens from a non-delimiting script are flagged and barred from filling the exact match slot. The asymmetry that forced this: bigram-to-bigram equality admitted 74.3% of a real Arabic corpus on a single query, against 6.9% for Greek through identical code. A shared two-character substring in an unvocalised abjad is simply not evidence. Whole-word containment carries the clitics instead, on the morphology channel where an approximate claim belongs.

Reaching a word's other forms

Five rules relate a query term to a word built on it: a suffix family, an inflection family, an agglutinative family, an Arabic root family, and a table of irregular forms no rule over shape can reach. Every one of them is pairwise — it answers a question about two strings and builds no equivalence class.

That constraint is the whole design, and it is why a stemmer was measured and rejected. A stemmer maps many words onto one class, so a single false friend poisons every member of it; snowball_stemmers_rs is spec-correct against 42,649 official test vectors and still merges Greek πολύ (much) with πόλη (city). A pairwise rule that is wrong costs exactly the pair it names.

Arabic needed a different tool again. It is a root-and-pattern language, so 144 roots poured into 20 templates generate 2,859 forms once, and two words are related only when one root explains both. That is an allowlist: a form the table cannot generate matches nothing. Three successive attempts to do it by subsequence all failed for the same reason — بيت→بيوت (a legitimate plural) and يجب→يجيب (two unrelated verbs) are the identical string operation, and no rule over shape separates them.

What each declaration costs

Morphology admits drawers rather than merely reordering them, so every rule has a price. None is hidden; each is held by a negative control that fails in both directions, so a cost disappearing is news that must be recorded rather than quietly absorbed.

A rule this layer learned the hard way

A recall measurement cannot justify a precision decision. The instrument used for most of this work counts how many words of a real 50,000-word vocabulary a query links to — it measures reach and is blind to whether a link is correct. Enabling -er for English moved that population figure by 0.21 links per query, indistinguishable from noise, while breaking five negative controls. Used to justify lowering a containment floor from 8 to 5, the same instrument admitted other/mother and count/accounting. Any rule that admits needs controls, not a link count.

Known limitation

Every figure above is within-language. Cross-lingual retrieval — an English query finding an Arabic drawer — is the embedder's job and the default cannot do it at all: HashEmbedder is feature hashing over surface forms, so a translation pair scores below an unrelated sentence, and car does not match automobile either. That needs a multilingual model via onnx/ort, or an external vault supplying its own vectors.

Dates, eras and calendars

A date in the text is read live at query time rather than stored, which is why a fix to a scanner or a change of declared locale reaches existing vaults with no migration at all.

The precedence is the interesting part. A caller can declare a calendar, but an era marker the writer typed beside the year — พ.ศ., هـ, 民國, 令和 — outranks that declaration. The reasoning is that a declaration is a statement about a whole corpus while the marker is the writer's statement about this one date, and reading it is evidence. Where markers on both sides disagree, they settle nothing and the declaration stands.

Field order resolves the same way: what you declared, else what an unambiguous date in the same text demonstrates (13/05 can only be day-first, so the writer has stated their convention by example), else what the language implies per CLDR (Arabic is d/M/y in every territory; English splits US from Commonwealth and therefore implies nothing), else day-first as a documented default.

The line this layer holds

A signal is read; a convention is declared; nothing is inferred. Script is not evidence — Thai script writes Gregorian dates constantly — and a numeral system is not a calendar: ๒๐๒๖ is an ordinary Gregorian 2026 typed in Thai digits, and reading the glyphs as an era claim once resolved it to the year 1483. Where no signal exists the honest answers are a documented default or a recorded-but-unresolved mention, never a confident value and never silence.

A wrong reading, and the signal that would fix it

١٩٩٥م is how Arabic writes a year and ١٥٠٠ م is how it writes a quantity — the difference is a single space. A bare م is therefore treated as an era marker when either a year noun governs the number or the marker is glued to it.

That disjunction misfires. In على ارتفاع ٢٥٠٠م — an altitude, 2500 metres — the year-noun test correctly fails, but the glued test fires on its own and the engine reads the year 2500. This is a gap, not a principled trade. The noun ارتفاع is sitting right there in the token stream: a year noun is already read as confirming evidence, and a measurement noun pointing the other way is precisely the same class of signal. It is simply not consulted yet. What would not be legitimate is a range check on the number — a value's magnitude is not evidence of its kind, which is the same line the calendar rules hold everywhere else.

Open gap

In-text date scanners exist for English and Arabic only. Greek and Russian now have full morphological paradigm coverage on the lexical channel and still cannot read a date written in their own text. The era, calendar and field-order machinery above is language-agnostic; the scanners that feed it are not.

Choosing a level

A vault is created sealed or hmac-only and keeps that level for life. The choice is about confidentiality only: integrity has no off switch at either level, so the question is never whether a row is verified but whether its bytes are readable to someone holding the file.

Keys, and why isolation is cryptographic

Per-vault isolation is not a WHERE clause that could be forgotten on one code path. Each vault derives its own encryption and MAC keys from the master key, and every sealed blob authenticates the vault id, the record id and the artifact domain alongside itself — so a ciphertext lifted into another vault, moved onto another row, or substituted for a different artifact does not decrypt.

The process — a write, a read, an open

The ordering below is the load-bearing part. Sealing, tagging and advancing the audit chain happen inside a single SQLite transaction, so there is no window in which a row exists without its audit entry; and the manifest anchor is written only afterwards, so it lags the database on purpose.

The chain records more than writes. Every export is chain-audited unconditionally and on every surface — one egress/export record binding the surface, the recipient, the record counts and the export's own payload digest, anchored like any write — because content leaving the palace is precisely the event a history is worth keeping about. Reads are audited only where a deployment declares it (UNDERCROFT_READ_AUDIT=chain), a per-query append being a real durability cost: one record per search carrying a keyed fingerprint of the query rather than its text, plus the declared scope and the hit count. An operator holding the key can later prove a specific query was run by recomputing that fingerprint; the record on its own says nothing about what was asked.

One boundary, stated

A read runs behind a shared reference and therefore does not advance the manifest anchor. That is the legitimate crash shape the open-time reconciliation already fast-forwards — but it means read records between two anchored writes share that crash window, and an attacker with write access to the file could strip the unanchored tail undetected while it lasts. A write never stretches the window beyond the single in-flight record; reads can. What closes it is the next anchored write, or the reconciliation the next store open performs — so a deployment that wants the anchor kept tight is one that writes on a cadence of its own.

What sealing does and does not cover

For sealed vaults there is an additional standing rule: no plaintext or plaintext-derived data is ever written to disk in clear. No full-text index exists for them, and search operates over decrypt-once RAM caches.

What that rule does and does not cover

It covers the content and everything derived from it that copies its words. It does not yet cover drawer metadata, which is stored unsealed. Measured against the bytes of a sealed database file, an attacker holding it reads twelve fields — counted from the test that pins them, not remembered: the wing name, the room name, the source_file path, added_by, the hall label, content_date, the dates resolved out of the content, the declared kind, the supersedes link (which record replaced which), and the writer's agent / channel / session claims — plus the clear filed_at / updated_at columns and each record's ciphertext size. They read no word of the content itself. In practice wing and room names are the topics, people and case identifiers, and a source path carries a username and a project name — so until this is closed, a deployment should treat those as public labels and keep the secret out of the name.

Two fields used to be worse. time_mentions[].text held every date expression as written and entities held every name, both lifted verbatim out of the content and both sitting in unsealed metadata. They are now emptied before the row is written; what survives is the resolutions — byte offsets and ISO dates, which are not content. The exposure that remains is pinned by a test that fails if content ever leaks and fails if a listed field stops being readable, so the inventory cannot quietly go out of date.

Closing the rest does not require giving up queryability, and the engine already contains both halves of the answer. Fields that must be filtered in SQL — wing, room — can become a keyed blind index: store a truncated HMAC of the value and filter on that, the shape duplicate detection already uses for its keyed fingerprint. Everything else moves into a sealed blob decrypted once into a RAM cache at query time, exactly as embeddings, PQ codes and ColBERT matrices already are. Sealing and searchability are not in tension here; the pattern for having both is already in use four times over.

Three things the knowledge graph paid for when it went first, all of which the remaining fields inherit. Copy the shape of that fingerprint, never its key: it is keyed with the vault's rotatable MAC key, which is right for a dedup lookup nothing holds a reference to and wrong for an index — re-keying a blind index means re-indexing the corpus, so the key is a per-vault secret stored sealed, which a rotation re-seals and never regenerates. Any unkeyed digest of the same value is the same leak: the graph's two ids were unkeyed SHA-256 of the words it was blinding, so an offline reader with a candidate list confirmed a guess by recomputing one, and blinding the column alone would have closed nothing. The same rule caught two more (U12): kg_triples.source_fp and drawers.supersedes_fp were unkeyed SHA-256 of a drawer's whole verbatim content, and are now keyed with that same stored secret — over the DIGEST rather than the content, so the at-rest migration re-wraps what is already stored instead of needing back the original bytes of a source that has since been edited. And the audit log carries these values too — it records each write under its subject's id, and holds wing and room names in clear today — so a field is not closed until its audit label is closed with it.

The defense program

Memory poisoning is the attack class this store answers at the write path: screen at the door, bound what a bad drawer can reach, and make every destruction hand back a proof.

The documented attacks on agent memory (MINJA, AgentPoison, forged reasoning) share one shape: poison enters through a save surface, waits in storage looking like memory, and fires when a retrieval puts it in front of a model. Systems that only defend at retrieval time let the poison become retrievable first. undercroft screens at ingest — no surveyed competitor screens the write path at all — and everything below ships as a deployment's declaration, never as a surprise: with nothing declared, the write contract is byte-identical to a vault that has never heard of any of this.

One boundary first, stated rather than implied: this program secures the memory and memory→agent zones. The agent→host zone — an over-privileged agent induced into a malicious tool call — belongs to the agent runtime's and OS's sandbox. undercroft is an inert store that never executes retrieved content, so it is never the code-execution vector; what it can do is refuse to become the delivery vehicle.

Trust is assigned; a claim is evidence

Two kinds of provenance exist, and the design never confuses them. Claims — agent, channel, session — are the writer's own statements, recorded on every save surface, HMAC-covered so they cannot be quietly rewritten, and deliberately never a trust boundary: poison must not admit itself by declaration. Assignments come from the operator: wing trust classes (quarantined | standard | trusted) are set over CLI and REST — deliberately never over MCP, the surface agents hold — HMAC-tagged and chain-audited, so a flipped class is an integrity failure, not a policy change.

An assigned class is consumed as a candidate-set floor (min_trust on a request, UNDERCROFT_TRUST_FLOOR on a vault) through the same scope machinery every other filter uses: resolved before candidates are drawn, so a quarantined wing that owns the corpus-wide top-k can neither answer a floored query nor crowd its candidates out — the starvation defect class, closed once for scopes, is closed here by construction. The doctrine is written down in docs/LABELS.md: filter, then weight; labels never enter scoring; cost is not trust.

Admission — screened at the door

With UNDERCROFT_ADMISSION=quarantine declared, every save that does not come from a deployment-trusted surface passes a two-tier detector. Tier 1 is deterministic — pure functions over the candidate bytes plus its deterministic hash embedding, no model, no network — and emits a closed vocabulary of signal codes with byte offsets, never content: imperative-instruction, tool-call-syntax, exfil-marker, encoded-blob, fixture-similarity, and rate-anomaly.

The last two closed the detector's stated wishlist. Fixture similarity compares 32-word windows of the candidate against a committed corpus of eighteen attack payload shapes by hash-embedder cosine — window granularity because whole-text cosine dilutes a short injection inside a long drawer to invisibility. It exists for the variant: a paraphrase that dodges every marker substring still shares the fixture's surface vocabulary, and surface overlap is exactly what the hash embedder measures. Its threshold is pinned from both sides — hard negatives (security prose about injection, an instructions-shaped onboarding note) measured ≤ 0.369, marker-dodging variants ≥ 0.540, threshold 0.45 — and validated at corpus scale: 0 of 5,882 clean LoCoMo turns flagged; 18 of 18 fixtures trip their own screen (the screenfp bench instrument, which fails hard if either side slips). The rate screen is the tier-1 signal candidate bytes cannot carry: a declared per-writer budget (UNDERCROFT_ADMISSION_RATE=<count>/<seconds>) checked against the vault's own committed history — the runaway-agent bound. It is declared, never defaulted, because a busy legitimate agent and a runaway one differ only by the deployment's own expectations; an unreadable declaration refuses to open rather than silently running unscreened.

Tier 2 is an optional local model (UNDERCROFT_ADMISSION_LLM=advisory) and is advisory-only by construction, in both directions that matter: consulted only for candidates the deterministic tier passed, and only able to push toward quarantine — a tier-1-flagged candidate is never shown to it, so content that talks the classifier into “clean” bypasses nothing. A failure to answer is a non-event, never a blocked write.

Where the screen sits is itself a decision, and the first version of it was wrong. Screening used to be applied at each call site, and a surface audit found three ways to walk straight past it on /v1 alone: a dedup_threshold in the save body routed to the dedup writer; a caller-supplied vector routed import to the raw writer — and /v1 export emits a vector on every line, so the ordinary backup-restore round trip and the orchestrator's tenant migration both re-admitted a whole corpus unscreened; and vaults with an external embedder had no screened path at all. None of those was a missing rule. Each was a call site someone forgot, and nothing in the design could have told them. The screen now lives at the one choke point every write funnels through, behind a required argument: a new write path does not compile until its author states a screening decision, and each of the few legitimate bypasses — an operator ruling re-filing a drawer, the diverted copy on its way to quarantine — is one greppable token carrying the reason it is allowed. A test walks every public write entry point with the screen on and requires the poison to end up quarantined, so the next forgotten call site fails there rather than in production.

The consequence is a contract worth stating plainly: a diverted save says so on every surface. The write returns the id the drawer actually landed under, not the one it aimed at — /v1 answers 202 with quarantined: true, MCP and the CLI say in words that the write is not retrievable. The earlier writer returned only "was this id new", which let all three surfaces report success against an id whose content was sitting in quarantine.

Quarantine, and the two rulings

A flagged save is diverted, never rejected and never silently dropped: it lands sealed in the reserved quarantine-pending wing with its signal codes and intended destination in metadata, hard-excluded from every read that returns content except a reviewer's explicitly named scope. Every read, which was not always true: the exclusion lived in search alone, so a diverted drawer was invisible to a query and then handed to the agent verbatim by the recent feed that wake_up serves, and listed by the drawer index behind the closet — the two surfaces whose whole job is loading context at session start, which is exactly where injected text wants to be. The wing refuses forged residents, quarantined drawers are not editable (the reviewer rules on exactly what the screen saw), and the update path is screened on the surface writing now — added_by is re-stamped before the screen, so an untrusted surface cannot ride the original writer's standing, and a flagged update leaves the drawer's previous content in place. allow re-files the drawer where it was headed (the human ruling is the override); deny destroys through the attested-forgetting path and hands back the receipt. Both rulings are chain records with the verdict inside the tag's canonical: the review trail is as tamper-evident as the data.

Review happens over CLI and REST — never MCP, and MCP will not so much as read the queue. One check over the raw argument map, in front of every tool call, refuses any argument that names the reserved wing and any id-shaped argument naming a drawer resident in it: the agent whose write was quarantined can neither read the evidence back nor delete it. Being a rule about arguments rather than a clause per tool, it covers arguments that do not exist yet — the point, given that the failure this whole section describes is a checklist going stale. Two prices are pinned rather than hidden. It matches the value, not the key, so saving a drawer whose entire content is the literal string quarantine-pending is refused too; and the wing's existence is not concealed — it still appears in the taxonomy with its count, because hiding a review queue from its own inventory buys nothing once naming it is refused.

Operator surfaces, and the read-only posture

Which capability exists on which surface is enforced, not documented. The MCP tool inventory lives in code, and the server is counted against it in both directions: a tool the server advertises without an entry fails, and an entry naming a tool that no longer exists fails too — the second half being what stops an inventory becoming the stale table it replaced. Beside it sits the shorter and more interesting list, the capabilities that must never appear on MCP: admission review, wing trust assignment, retention, attested forgetting, key rotation. That is not a parity gap waiting to be closed. MCP is the surface an agent drives, and an agent must not be able to rule on the queue that exists to contain it, nor assign the trust class that decides what it may retrieve.

serve-http --read-only is a posture on the process, not a filter on one port. That process opens two handles on the same vault — one behind /mcp, one per tenant vault behind /v1 — and for a while only the second honoured the flag, so a "read-only" server re-embedded every drawer of its --vault vault at start-up and, under UNDERCROFT_READ_AUDIT=chain, appended a chain record per /mcp search: whether the vault was written depended on which door you came in by. Both handles now take the same posture, as an argument a caller must state rather than a flag that can default. And the route gate sits in front of dispatch, failing closed: a request mutates unless it is a GET or one of two named POSTs, so a route added later is refused on a read-only server until someone deliberately allows it — the opposite of the per-handler guard it replaced, where forgetting one line opened a write door and nothing said so. POST …/kg/authority was exactly that forgotten line, and is refused now. The two exceptions are POST for cost rather than for effect: search reads, and verify walks every row's HMAC, replays the chain, and checks four more things nothing else can see — every drawer supersession receipt, every knowledge-graph fact receipt, every graph audit label, and every clear mirror column against the covered copy.

The boundary is stated rather than blurred, and since 1.0.0 it includes the open. That sentence used to read the other way — a read-only open still created schema, reconciled a rotation and initialised the chain, so the posture protected the vault's contents from the traffic it served but not the file from every byte. It now opens the connection SQLITE_OPEN_READ_ONLY under PRAGMA query_only=ON, so a write nobody thought of fails loudly instead of happening quietly; the schema is checked rather than created; a lagging manifest anchor is reported rather than fast-forwarded; and an interrupted key rotation is honoured in memory with its vault.json.next left exactly where it is — the operation the incident-response runbook's own "freeze writes" step was performing on a suspected-compromise vault. Everything the open declined to repair is warned once and then readable as unhealed on undercroft stats, undercroft_status and GET /v1/vaults/{id}/stats. Three more things that would otherwise write instead decline and say so: the embedder migration warns and serves the old vector space rather than rewriting it (the replica precedent — a replica exists to answer across configuration drift), read auditing is force-disabled because an audit record is a write, and a prefilter tier loads an existing index but never builds one, falling back to the exact scan and announcing it once per tier. GET …/export is served for the same reason, with a warning that its egress/export chain record was skipped.

Two conditions refuse rather than report, because serving through them answers a question wrongly rather than partially. A manifest whose palace.db is absent is a 409 naming the file: Connection::open carries SQLITE_OPEN_CREATE, so a half-copied backup or a snapshot taken mid-write used to open "successfully" against a fabricated empty vault and answer every read empty with no error — "empty" is not "absent", and this one is an integrity verdict, so the CLI exits 2. A schema this build would have had to migrate is the other, also 409: migrating means every ALTER TABLE … ADD COLUMN in the named column inventories (counted by a test rather than written here, because the number in this sentence was twelve while the tree ran fourteen), and the honest answer is to name what is missing and ask for one writable open. Neither is a crash a replica must survive — a vault whose writer died mid-rotation still opens, which is the case that made reporting rather than refusing the rule everywhere else.

Destruction is receipted

C3.2's rule is that forgetting must be provable and deletion must never be quiet. forget produces a chain-attested receipt — the chain heads before and after, the exact tombstone interval, and unkeyed content fingerprints of what was destroyed. The vault itself verifies an attestation by keyed replay; a third party without the key verifies the operator's Ed25519 signature over it, and that asymmetry is stated rather than blurred. Retention policies ride the same machinery: declared per wing or room (operator-only, HMAC-tagged, audited — a flipped policy fails both listing and sweep), enforced only by an explicit sweep that goes through the receipted path, never automatically at open. The sweep's clock is the HMAC-covered filed_at inside each drawer's tag — a flipped clear column can neither launder a deletion through a keyed sweep nor hide a drawer from its declared retention. And superseding never deletes: a correction records what it replaced under the drawer's HMAC with a keyed receipt over the superseded content's fingerprint — itself keyed with the stored graph secret since U12, so it survives a rotation without being a confirmation oracle at rest — five verdicts distinguishable at verify.

What a poisoned drawer cannot do

Screening is heuristic, so the retrieval layer assumes some poison gets through — and bounds it. The standing invariant: independent per-item scoring. The default embedder is a function of one drawer's text, MaxSim maximises over one drawer's rows, the admission gate is a constant, and the lexical channels are deliberately pairwise — so a poisoned drawer can win its own slot and nothing else. Anything that couples drawers (BM25's IDF, the trained codebooks) may propose candidates, never decide score; coupling in candidate generation risks availability, coupling in scoring would move what decides the answer outside HMAC coverage. BM25's IDF is the one exception, and it is stated rather than hidden: it is computed over the retrieved candidate pool, not the corpus (bm25_raw takes n = cands.len() and counts df across that slice), so a drawer that merely enters the pool shifts every other candidate's score. Making it corpus-global would add coupling, not remove it, so the honest accounting is the cost: pool-shaping makes df-flooding cheaper than a corpus-wide count by roughly corpus/pool — bounded to rank order inside one answer, never reaching HMAC-covered bytes. The codebooks' training draws are bounded three ways: vectors are L2-normalized before training, so influence is bought by count, not magnitude; a per-wing cap holds any wing to a fraction of every global sample (with a per-agent-claim cap as the accident bound across wings); and which rows train is a stratified keyed draw under a vault-secret key — reproducible per vault, unguessable to a bulk writer. Non-finite vectors from a caller-supplied embedding space are refused at the door. Since the per-wing index tier, a wing is an enforceable trust zone for scoped retrieval: poison in another wing can neither crowd a scoped query's candidates nor shape the codebook scoring them.

Nothing crosses a wire in the clear

Every path that carries drawer content out of the process obeys one transport rule with no override: TLS or loopback, or it refuses to construct. The served embedder (UNDERCROFT_EMBEDDER=http) and every LLM consumer (refine, the admission advisor) refuse cleartext http to a non-loopback host, with the error naming the fix; UNDERCROFT_EMBED_CA and UNDERCROFT_LLM_CA declare self-signed roots as pins — public roots out, a garbage file refusing rather than silently un-pinning — and the compose embeddings-tls terminator ships the compliance infrastructure beside the refusal. What TLS cannot do is also stated: the endpoint still reads your text in plaintext, which is why the in-process postures exist. Remote vector indexes obey the same rule since 1.0.0, and that is a gap closed rather than a design always held: they had no transport policy at all, and pgvector was wired NoTls — so for that backend no TLS-compliant configuration existed. The argument for applying it there is that every push carries embeddings, and an embedding is plaintext-derived: the sealed-vault invariant seals vectors at rest for exactly that reason, so shipping them in clear over a network is the same exposure one hop out. UNDERCROFT_INDEX_CA pins a self-signed root, pgvector gets a real rustls connector, and the rule itself now lives in one crate (undercroft-net) that all three clients call, because two copies of one rule is two places for it to drift. They remain untrusted accelerators — at-rest content only, candidates re-verified locally, never a scoring authority — and an hmac-only vault, whose at-rest content is the plaintext, is refused unless the operator states otherwise.

They are now held to the same retrieval policy as well, and that is a defect closed rather than a design always held: the closed-vocabulary checks, the trust floor and the quarantine fence all come out of one shared, required resolution step that the local and the remote search path both call, applied per candidate off each row's HMAC-verified wing. The remote path validated none of it, so an index push quietly turned --backend qdrant into a route around admission control — the same query answering with quarantined content and below-floor wings that --backend local hard-excluded. The fix is a shared step with a name, not a second copy of the rules; any future retrieval path has to call it too. One residue is stated rather than papered over: a push still mirrors quarantined rows, because a push-side filter is not a boundary (an untrusted mirror can offer any id it likes) and dropping them would empty the reviewer's own scope. Remotely, then, the floor bounds what comes back rather than what was generated — an availability cost, never an integrity one.

Honest boundaries

Detection is heuristic and says so: poison written without any marker, fixture vocabulary, or rate signature passes the screen; a security engineer's own notes about prompt injection can trip it. That is exactly why a signal quarantines for a human instead of rejecting, why the signal vocabulary is closed (the review queue reads as data), and why the quarantine log is the stated source of future fixtures. Provenance claims bound accidents, never adversaries — a deliberate attacker rotates claims, which is why the caps keep a surface-grouped floor and the wing grouping stays the adversarial bound. And a poisoned drawer that wins its own slot still reaches the reader: retrieval bounds the blast radius; it cannot make a lie true.

Configuration reference

Everything is environment-driven, and every default is the conservative choice. What a bad value does follows from that: where the default is already conservative and a declaration merely adjusts it, garbage warns and keeps the default — you lose tuning and nothing else. Where the declaration is what turns a protection on, pins an outward path, or names which vector space a vault is in, the default is off, so a silent fallback removes exactly what was asked for: those refuse to open. That is “integrity is not a tier” extended by one step — a protection an operator declared must not become a tier by typo. undercroft config check runs every declaration through the resolver that runs at start-up, opens nothing, and exits non-zero if the environment would refuse; the classes are an inventory the code is counted against in both directions, so a new variable cannot ship unclassified.

Why the defaults are what they are

Almost every optional tier is off. That is a position, not an oversight.

Approximate tiers are opt-in

PQ, FDE, and HNSW trade exactness for speed. A memory product that silently loses recall to save milliseconds has broken its main promise, so each stays off until measured on the workload in question.

Models are user-supplied

No weights ship with the binary and none are downloaded. The default embedder is a deterministic hashed n-gram — offline, reproducible, and adequate on its own.

Outward paths are explicit

No LLM URL, no OTLP endpoint, no remote index, no API key by default. Each is one variable, and setting it is a visible decision about data leaving the machine.

Integrity is not a tier

Verification, sealing, and the audit chain have no off switch. They are the parts you cannot bolt on afterwards.
